# Hau'oli growth ブログ 執筆ガイド（正本）

「何を書くか」「どう書くか」の正本。小林顕人本人、ちびあっきー（ChatGPT）、Claude Code の全員がこれに従う。
ファイルの置き場・frontmatter の全項目・ビルドや公開の手順は [README.md](README.md)（技術仕様）。ここには書かない。

## 1. このブログは何のためにあるか

普段の仕事・壁打ち・Reel・実務から生まれた小林顕人の思考と判断基準を、会社の資産として残す場所。
ブログは新しい業務ではない。**普段の仕事から生まれた思考を、記事の形で残す仕組み**。

蓄積するもの:
- 小林顕人の思考、Hau'oli growth の判断基準
- マーケティング／経営・組織／人材育成／AI・仕組み化に対する考え
- 実務から生まれた判断方法

読者に「Hau'oli growth はこうやって考えるんだ」「小林に相談すると、こういう風に整理されるんだ」「単に広告を触る人ではないんだ」と分かってもらう。

読んだ人に起きてほしいこと:
- Hau'oli growth の考え方・取り組み方が深く分かる
- 書いている人がどんな人間なのかが分かる（今は小林顕人。いずれスタッフも書く）
- Hau'oli growth をもっと好きになる
- 一緒に成長したいと思ってもらえる

ブログは Instagram の続き（深掘り版）ではない。Instagram より先に考えを出してよい、**これまでの知識と積み重ねの保管庫**。Reel が元になる記事も、話したままではなく記事として読める形にリライトする。

SEO / AI検索への技術対応は仕組み側でやる。**そのために文章を一般的な解説記事に寄せない。**

Claude Code が文章上の修正を必要と判断した場合は、勝手に直さず「どこを・なぜ」を示して確認する。

## 3. Voice

**小林顕人がその場で相手に話しているような文章**が基本。Reel の Voice とブログの Voice は同じ人物。

例:
> 広告の数字が悪くなると、
> 「これ、作り直した方がいいですか？」
> って話になるじゃん。

> でも俺、
> 調子が悪い＝作り直す
> では見てないんだよね。

> ここ、結構大事なんだけど。／そもそも今、何が起きてるんだっけ？／これって誰の何がどう変わるんだろう？／一回分けて考える。／結論、今何してんだっけ？

**重要: 口癖をテンプレ的に入れない。** 「俺は〜と思ってるんだよね」「〜じゃん」「だからね」「でね」「俺はね」を無理に散らさない。
Voice は単語の真似ではない。**小林の思考順序・問い・判断の仕方が自然に文章に出ていること**を優先する。

## 4. NG

- SEO記事っぽい無機質な文章／教科書口調／コンサル資料のような文章
- 専門用語で賢く見せる／一般論による水増し
- 元情報にない体験談／小林が言っていない出来事を事実として追加
- 元情報にない数字の追加／もっともらしい推測を事実として追加
- 不要な「正解か分からないけど」「まだまだですが」／過剰な「〜すべき」
- SNS用の名言を作ることを目的にする
- 全部説明しようとして必要以上に長くする

## 5. 技術記事の事実確認ルール

**確認済みの元情報（brain-hub の記録、本人の発言・壁打ち）に存在しない数値・主張・条件を増やさない。**
補足したくなったら、推測で足さず「ここは記録に無い」と本人に返す。
使った出典は frontmatter の `sources` にメモとして残す（表示されない。後で照合するため）。

## 6. 記事の基本構造

絶対固定ではないが、基本はこの流れ:

1. 現場でよく起きること
2. 小林が感じている違和感
3. 「それ、本当に○○？」という問い
4. 問題を分解
5. 判断基準を整理
6. 必要なら技術詳細・表・図
7. 小林ならどう判断するか
8. 読者が持ち帰れる判断基準

**情報を全部載せることではなく、読者が判断できる状態を作ること。**

### 記事の長さ

- 通常記事は **3,000〜5,000文字程度** を目安にする。固定ルールではなく、読者が一つの主張を無理なく理解できる長さを優先する
- **5,000文字を超えそうな場合は、別のGoal・主張・読後感を持つ論点が混ざっていないか確認する**
- 2つの独立した主張に分けられるなら、無理に1記事へ詰め込まず2記事へ分ける
- 5,000文字超でも、専門解説や一つの論点を理解するために必要な場合は長文を許容する
- 長さを埋めるための一般論・重複説明は追加しない。**一記事一メッセージを優先する**

### タイトルと FIRST ANSWER

- H1はVoice優先。検索意図がH1だけでは分かりにくい時だけ frontmatter に `metaTitle` を使う（ページの表示H1はそのまま）
- 導入の早い段階に **FIRST ANSWER** を置く。2〜5行程度で、その記事の結論・分類・判断順など「AIや人間が最初に答えを掴める形」にする
- ただしSEO記事口調にはしない。小林のVoiceのまま差し込む

### 文脈CTA（中間CTA）

- 長文記事では、記事内容と自然につながる箇所に中間CTAを **1個まで** 置いてよい
- 売り込みではなく「自社の場合どう整理するか」の相談導線。`[相談する](/#contact)` の形で `/#contact` にリンクする
- Markdown本文の `/#contact` リンクは自動で `blog_inline` として計測される（末尾の共通CTAは `blog_post` で別計測）
- 毎記事に義務化しない。記事の役割に合う場合のみ

## 7. 書式（表示に直結する）

### 改行
短い改行や「間」は文章表現の一部。**ブログ本文では Markdown の1行改行がそのまま改行として表示される**（本文レンダラーのみの設定。サイト全体には適用していない）。
- 息をつく所で改行する。1行は短く
- 段落を分けたい時は空行を1つ

```
でも俺、
調子が悪い＝作り直す
では見てないんだよね。
```
↑ このまま3行で出る。1行に潰れない。

### 見出し
- 記事タイトル = H1（ページ側で出力。**本文で `#` は使わない**）
- 大見出し = `##`
- その配下（A〜D の型、判断パターン等）= `###`
- 必要な場合のみ `####`

```
## 俺は「誰が直せるか」で4つに分けてる
### A｜追随ラグ型
### B｜位相ズレ型
```

章の間の `---`（区切り線）は使ってよい。

### 表
比較や判断順など、**表にした方が理解が速い場合だけ**使う。文章で言えるものを無理に表にしない。
先頭列は折り返さない設計なので、先頭列には短い語（「D 信号汚染」「1」など）を置く。スマホで崩れないことは Claude Code が確認する。

### 強調
太字は `**…**`。「」の外側に置く（`「**強調**」`）。`**「…」**` の形は太字にならないことがある。

## 10. draft

- 原稿は**必ず `draft: true` で置く**。ちびあっきーの完成原稿も、Bridge 経由の原稿も例外なし
- draft は `npm run dev` と Vercel の Preview デプロイでだけ見える。本番（main）には出ない
- draft を外すのは、小林の承認後に Claude Code がやる（下記フロー参照）

## 11. アイキャッチ

- **通常記事: 何もしない。** ビルド時に title / category / author からブランドテンプレ（黒・白・ゴールドの4種、カテゴリで自動選択）で 1200×630 を生成し、一覧と OGP に使う。AI画像APIは使わない
- **特別な記事だけ**: GPT等で作った画像を `public/blog/<slug>/` に置き、frontmatter に `cover: /blog/<slug>/xxx.jpg` を書く。自動生成より優先される
- タイトルはそのままアイキャッチに流し込まれる。32文字前後まで

## 12. 記事作成〜公開フロー

```
STEP 1  普段の仕事・壁打ち・Reel からテーマが生まれる
STEP 2  小林「これブログにして」→ ちびあっきー（将来はちびあっきー側から候補提案も可）
STEP 3  ちびあっきーが完成原稿をチャット上で小林へ提示する
        （title / metaTitle / description / slug / category / 本文 / CTA を含む最終形）
STEP 4  小林が「OK」「公開して」等を明示する
        → この承認は「内容承認＋公開承認」を兼ねる。以後は再承認不要
STEP 5  ちびあっきーが、承認済み原稿＋内部リンク差分＋related を公開用Markdownへ反映し、GitHub main へ公開反映する
        必要な技術変更がある場合だけ Claude Code を使う
STEP 6  main 反映まで終わったら、会話は公開完了を待たずに次の記事へ進む
        Vercel の build / deploy は外部側で進む。公開待ちで制作ラインを止めない
STEP 7  次の会話ターンで未確認の公開があれば、ちびあっきーが GitHub / Vercel 状態を確認する
        success → 「ちなみに前の記事、公開完了してるよ」と短く共有
        failed / 想定外差分 → 先に共有して対応する
        ※ 本番確認前に「公開完了」とは言わない
```

### 内部リンク・回遊設計（公開時に必ず実施）

新しい記事は、単体で公開して終わりにしない。公開のたびにブログ全体のつながりを更新する。

- **新記事 → 過去記事**: 文脈が強くつながる記事を1〜2本、本文中から自然にリンクする。
- **過去記事 → 新記事**: 全過去記事のタイトル・主張を見て、新記事が補足・具体化・続きになる記事だけ逆向きリンクを追加する。
- 過去記事から後から公開された記事へリンクする時は、「次の記事で」「後から書いた」など公開順に依存する表現を使わない。「この論点は〜で詳しく書いている」のように、いつ読んでも自然な表現にする。
- 記事末尾の `related` は原則3本。関連が明確な場合は自動選択に任せずslugを明示する。
- SEO目的だけの弱いリンクは入れない。リンク0本が自然なら無理に作らない。
- 人間にリンク管理表は作らせない。公開担当AIが新旧両方向を確認し、必要な差分だけ更新する。
- 過去記事の本文・内部リンク・related などを**意味のある形で更新した場合だけ**、frontmatter の `updated` を実際の更新日にする。単なる再ビルドや見せかけの鮮度更新では変更しない。

つまり公開は、**「1本追加」ではなく「ブログ全体の知識構造を1回更新」**として扱う。

### 公開待ちを制作ラインから外す

Goal は「公開作業を速くする」ではなく、**公開待ちで次の記事制作を止めないこと**。

- 原稿・内部リンク・逆向きリンク・related の品質判断は、承認前に終わらせる
- 小林が「公開して」と言ったら、GitHub main への反映まで即実行する
- main 反映後は Vercel の build / deploy 完了を待たず、次の記事の壁打ちへ進む
- Vercel は外部サービス側で継続するため、ChatGPT が裏で処理を続ける前提にはしない
- 次の会話ターンで未確認の公開があれば状態を確認し、成功なら短く完了報告する
- failed / 競合 / 原稿との差異 / 想定外変更だけ人間へ戻す
- 複数記事の制作は直列にしない。**パス相手がいる仕事を先に進め、自分だけで完結する確認は人を待たせない**

これをブログ公開の標準運用とする。

**品質学習について**: 最初の10〜20記事は、完成原稿をチャットで事前提示（STEP 3）することで「小林らしい文章か」「直されるポイント」を学ぶ。preview 確認後の二重承認は不要。

進行状況と結果は管理画面 https://admin.hauoil.com の **Content** で見る（公開／下書き／企画中、記事別の閲覧数・問い合わせ数）。
企画中のテーマは Content の「企画を追加」で slug と仮タイトルを置いておく（記事ファイルができたら自動で同じ行に繋がる）。

### 公開前チェックリスト（Claude Code）
- [ ] `npm run build` 成功
- [ ] PC / mobile 表示（横はみ出しなし、表が崩れていない）
- [ ] 改行が原稿どおり出ている
- [ ] 本文に H1 が無い。大見出し H2、配下 H3
- [ ] title / description / canonical / OGP（記事の cover.png または独自画像）
- [ ] 構造化データ（BlogPosting + BreadcrumbList）に title / date / author が正しく入っている
- [ ] sitemap.xml / feed.xml / blog/index.json に記事が入っている

- [ ] 過去記事 → 新記事で追加すべき逆向きリンクを確認した
- [ ] 関連記事が出ている（原則3本。関連が明確なら `related` 指定）
- [ ] 記事末尾の CTA → `/#contact` に遷移し、フォームの参照元に `post=<slug>` が入る
- [ ] 元情報に無い数値・主張が足されていない（`sources` と照合）

## 13. 将来（Bridge 接続）

ちびあっきー → Claude Code Bridge → hauoli-site を直結し、人間側にコピペや Markdown 作成を発生させない。
サイト側の受け口は今のまま `npm run new-post -- --json`（title / description / slug / category / author / date / body / source_notes / custom_cover の構造化データ）。API の追加は不要。
Bridge が繋がっても、完成原稿のチャット提示 → 小林の承認 → draft 配置 → push の順は変えない。
